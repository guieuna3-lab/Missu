# figma-build: Figma 와이어프레임 → 코드

## 이 스킬이 존재하는 이유

사용자는 컴퓨터공학 전공자지만 프론트엔드·디자인 용어가 익숙하지 않아서 요청을 추상적으로 말하는 편이다. "깔끔하게", "저기 그 부분", "디자인처럼" 같은 말은 사용자의 머릿속에서는 구체적이지만 코드로는 여러 가지로 해석된다. 추측해서 구현하면 사용자가 결과를 보고 "그게 아닌데"라고 하는 왕복이 반복되고, 그 왕복이 컨텍스트를 오염시킨다.

그래서 이 스킬의 핵심은 **구현 전에 추상적인 요청을 Figma 노드 + 기존 코드 + 완료 기준으로 번역하고, 그 번역을 사용자에게 짧게 확인받는 것**이다. 확인은 길게 묻지 말고, 네가 본 것을 바탕으로 "이렇게 이해했는데 맞아?"로 좁혀서 묻는다. 질문은 한 번에 최대 3개, 가능하면 선택지(AskUserQuestion)로.

## 작업 순서

### 1. 요청 해석 — 무엇을, 어디에

사용자의 말을 아래 세 가지로 쪼갠다. 비어 있는 칸은 Figma와 코드를 **먼저 확인한 뒤** 질문한다. 확인 없이 질문하면 사용자가 모르는 용어로 되묻게 된다.

| 칸 | 채우는 방법 |
|---|---|
| **대상** (어느 화면·컴포넌트) | Figma 링크/노드 이름이 있으면 그것. 없으면 Figma 파일의 프레임 목록(get_metadata)을 가져와 후보 2~3개를 보여주고 고르게 한다. |
| **작업 종류** | 새로 만들기 / 기존 코드를 디자인에 맞게 수정 / 디자인과 다른 부분 찾기 중 하나. |
| **완료 기준** | 사용자가 말하지 않으면 네가 제안한다. 예: "Figma 프레임과 레이아웃·간격·텍스트가 일치하고, 타입체크와 린트가 통과하고, 브라우저에서 열어 비교했을 때 눈에 띄는 차이가 없음." |

추상적인 표현은 아래처럼 구체 질문으로 바꾼다. 사용자에게 용어를 가르치려 하지 말고, 스크린샷이나 선택지를 보여주며 고르게 한다.

| 사용자가 이렇게 말하면 | 실제로 확인할 것 |
|---|---|
| "깔끔하게 / 정리해 줘" | 간격(여백)이 일정하지 않은지, 정렬이 어긋났는지, 글자 크기 위계가 없는지 — Figma와 비교해 어느 것인지 짚어서 보여준다 |
| "디자인처럼 / 피그마대로" | 어느 프레임인지, 그리고 레이아웃·색·글꼴·간격 중 어디까지 맞출지(와이어프레임이면 보통 레이아웃과 구조만) |
| "저기 그 부분 / 위에 그거" | 스크린샷을 찍어 영역을 번호로 표시하고 번호로 고르게 한다 |
| "버튼 하나 추가" | 어떤 동작(클릭 시 무엇), 어디에 위치, 기존 버튼 컴포넌트가 있으면 그것을 재사용할지 |
| "반응형으로 / 모바일에서도" | Figma에 모바일 프레임이 따로 있는지, 없으면 기준 너비를 사용자에게 제안 |
| "안 예뻐 / 이상해" | 스크린샷 두 장(현재 vs Figma)을 나란히 놓고 차이 목록을 만들어 어떤 차이가 거슬리는지 고르게 한다 |

### 2. Figma 확인

1. 세션을 만들고(create_session) 대상 노드의 디자인 컨텍스트(get_design_context)와 스크린샷(get_screenshot)을 가져온다. Figma 도구를 쓰기 전에 그 도구의 스킬(/figma-design-to-code 등)이 있으면 먼저 읽는다.
2. 가져온 결과는 **참고용**이다. 그대로 붙여넣지 말고 프로젝트의 컴포넌트·스타일 방식에 맞춰 옮긴다.
3. 본 것을 사용자에게 **일상 언어로** 3~6줄 요약한다. 예: "상단에 제목과 뒤로가기, 가운데 카드 3개가 세로로, 맨 아래 고정 버튼 하나. 카드 안에는 이미지·이름·가격." 여기서 사용자가 "맞아" 하면 대상이 확정된다.
4. 와이어프레임에는 색·글꼴이 임시값인 경우가 많다. 프로젝트에 디자인 토큰이나 테마가 있으면 그것을 우선하고, 없으면 Figma 값을 쓰되 그 사실을 보고에 적는다.

### 3. 기존 코드 확인

구현 전에 반드시 본다. 사용자는 "이미 비슷한 게 있다"는 걸 모르거나 말하지 않을 수 있다.

- `package.json`으로 프레임워크·스타일 방식(Tailwind, CSS Modules, styled-components 등)·UI 라이브러리를 파악한다.
- 공통 컴포넌트 폴더(components/, ui/ 등)에서 재사용할 수 있는 버튼·카드·입력창·레이아웃을 찾는다. 있으면 새로 만들지 않는다.
- 같은 화면이 이미 있으면 "새로 만들기"가 아니라 "수정"으로 작업 종류를 바꾸고 사용자에게 알린다.
- 라우팅·상태관리·API 연결 방식은 기존 패턴을 따른다. 새 라이브러리는 추가하지 않는다. 꼭 필요하면 이유와 함께 먼저 묻는다.

### 4. 계획 확인 (짧게)

구현 전에 아래 형식으로 한 번만 보여주고 승인을 받는다. 변경이 파일 1개 안에서 끝나는 작은 수정이면 이 단계는 건너뛴다.

```
대상: <Figma 프레임 이름> → <파일 경로>
재사용: <기존 컴포넌트 목록>
새로 만듦: <컴포넌트/파일 목록>
수정: <파일 목록>
Figma와 다르게 할 것: <있으면 이유와 함께>
완료 기준: <1단계에서 정한 것>
```

### 5. 구현

- 요청한 범위만 건드린다. 주변 코드 정리, 이름 바꾸기, 타입 추가 같은 "하는 김에" 작업은 하지 않는다.
- 하드코딩된 더미 데이터는 한 곳(상수 또는 mock 파일)에 모으고 주석으로 표시한다.
- Figma와 의도적으로 다르게 구현한 부분은 코드 주석이 아니라 보고에 적는다.

### 6. 검증

"됐다"는 말 대신 증거를 보여준다.

1. 타입체크와 린트를 실행하고 결과를 그대로 보여준다.
2. 개발 서버가 떠 있거나 띄울 수 있고 브라우저 도구가 있으면, 해당 화면 스크린샷을 찍어 Figma 스크린샷과 비교하고 **차이 목록**을 만든다(레이아웃·간격·텍스트·누락 요소). 사소한 차이는 고치고, 판단이 필요한 차이는 사용자에게 보여준다.
3. 브라우저 도구가 없으면 "브라우저에서 <경로>를 열어 Figma와 비교해 달라"고 요청하고, 확인할 포인트를 3개 이내로 적어준다.

### 7. 보고

사용자가 코드를 전부 읽지 않아도 상황을 알 수 있게 쓴다.

```
무엇을: <만든/바꾼 것, 화면 기준으로>
어디를: <파일 목록>
왜: <재사용/구조 선택 이유, 한두 줄>
Figma와 다른 점: <목록, 없으면 "없음">
확인 결과: <타입체크/린트/스크린샷 비교 결과>
다음에 할 일 / 결정 필요: <있으면>
```
### 8. Git / GitHub 반영 (사용자가 "커밋해", "PR 올려"라고 했을 때만)

사용자는 git 절차를 배우는 중이다. 명령을 실행할 때마다 **무엇을 왜 하는지 한 줄**로 설명하고, 되돌리기 어려운 단계(push, PR 생성)는 실행 전에 승인을 받는다.

1. **상태 확인**: `git status`와 `git diff --stat`으로 바뀐 파일 목록을 보여준다. 이번 작업과 무관한 파일이 섞여 있으면 사용자에게 알리고 제외한다.
2. **브랜치**: main/master 위에서 직접 작업하지 않는다. 브랜치가 없으면 `feature/<화면이름>` 형식으로 만든다. 프로젝트에 브랜치 규칙이 있으면 그것을 따른다.
3. **스테이징**: `git add .` 대신 이번 작업 파일만 지정해서 add 한다. 왜: 실수로 들어간 파일이 커밋에 섞이는 걸 막기 위해.
4. **커밋**: 메시지는 `feat: 상품 목록 화면 구현` 형식(타입: 요약). 한 커밋은 하나의 의도만 담는다. 화면 구현과 버그 수정이 섞였으면 두 번 나눠 커밋한다.
5. **push**: 하기 전에 "브랜치 <이름>을 origin에 push할게" 하고 승인받는다. `--force`는 쓰지 않는다.
6. **PR 생성**: `gh pr create`를 쓴다. 본문은 아래 형식. 생성 전에 제목과 본문을 보여주고 승인받는다.
## 하지 말 것

- 추측으로 대상 프레임을 고르지 않는다. 후보가 둘 이상이면 보여주고 고르게 한다.
- 사용자가 모르는 용어로 되묻지 않는다. 용어가 필요하면 한 줄 설명이나 스크린샷을 붙인다.
- 질문을 다섯 개씩 늘어놓지 않는다. Figma와 코드를 보고 답할 수 있는 건 스스로 답한다.
- 테스트나 타입체크를 "통과했을 것"이라고 말하지 않는다. 실행 결과만 말한다.
